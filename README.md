# Общий кеш публичных запросов

`public` и `internal-public` используют одну роль ClickHouse `public_reader`.
Она содержит существующие публичные права чтения, включая частичные запреты
на колонки `systemInfo.*`. Пользователь `internal-public` имеет пароль и не
получает квоту `public`; настройки запросов совпадают с `public`.

## Протокол кеша

Основной Nginx, RU и Cloudflare допускают общий кеш только для двух точных имён:
`public` и `internal-public` в HTTP Basic Authorization. Cookies, альтернативная
авторизация `X-ClickHouse-*`, параметры `user/password/session_id/session_check`
по-прежнему исключают запрос из общего кеша. Остальные пользователи проходят BYPASS.

Группа кеша (`scope`) для обоих аккаунтов — `public`. Клиент использует её явно;
Nginx определяет группу через `map $remote_user`, Worker — по имени в Basic.
Имя пользователя и пароль не входят в хеш. В ClickHouse передаётся исходный
Authorization без подмены, проверки пароля перед поиском в кеше нет.

Ключ — SHA-256 в виде 64 шестнадцатеричных символов от JSON-массива:
`['wotstat-clickhouse', 'public', 'POST', sortedParameters, policy, sql]`.
Nginx и Worker разделяют записи по группе и ключу. После выкладки кеш прогревается заново.

- HIT возвращает публичные данные без проверки пароля, в том числе при неверном пароле.
- MISS/BYPASS проверяет ClickHouse. Ошибки авторизации не кешируются.
- Заполнение кеша требует успешного ответа и проверенного хеша SQL/параметров/политики.
- Кеширование включается клиентом явно: `proxyCache: true` вместе с политикой `cache`.
  Запросы к текущему пользователю/сессии выполняются без общего кеша.

В эту группу нельзя добавлять приватные права, запись или зависящие от пользователя
row policies. Роль ClickHouse не вычисляется на каждом HTTP-запросе: это договорённость
конфигурации. Изменения прав чтения в дальнейшем выдаются роли, не отдельным пользователям.

## SQL для существующего сервера

SQL подготовлен по чтению production через MCP 2026-10-15, версия 26.9.8.3:
114 GRANT/REVOKE, 203 записи `system.grants`, без ролей и row policies у `public`.

1. Сохранить `SHOW CREATE USER public`, `SHOW GRANTS FOR public` и настройки квот.
2. Администратором выполнить `clickhouse/migrate-public-reader.sql` через
   `clickhouse-client --multiquery`. Скрипт проверяет отпечаток текущих прав,
   создаёт роль со всеми GRANT и частичными REVOKE, сравнивает её со снимком,
   назначает роль по умолчанию и только затем снимает прямые привилегии `public`.
3. Выполнить `clickhouse/create-internal-public.sql`, передав непустой параметр
   `--param_internal_public_password="$CLICKHOUSE_PASSWORD"` и `--multiquery`.
   Пароль не хранится в SQL. Учётка ограничена `HOST LOCAL`, поскольку Nginx
   соединяется с ClickHouse через `127.0.0.1:8123`.
4. Проверить `SHOW GRANTS FOR public`, `SHOW GRANTS FOR public_reader`,
   `SHOW GRANTS FOR \`internal-public\`` и отсутствие квоты у новой учётки.

Оба скрипта нужно запускать с остановкой на первой ошибке, без `--ignore-error`.
DDL не транзакционный. При изменении прав после снимка миграция остановится до
изменений; нужно обновить снимок. Повторный запуск после частичного выполнения
требует проверки выполненных шагов. Скрипты не удаляют существующие роли/пользователей.
`clickhouse/setup.sql` предназначен только для начальной установки, не для миграции
рабочего сервера. На рабочем сервере эти SQL автоматически не применяются.

## Порядок публикации

1. Применить SQL, затем обновить `njs/query-cache.js`, `conf.d/query-cache.conf`
   и `snippets/query-cache.conf` на основном и RU Nginx. Проверить `nginx -t`
   и перезагрузить конфигурацию.
2. Опубликовать `cloudflare/query-cache/worker.js` через существующий Wrangler-проект.
   Обновить все слои кеша до публикации нового клиента.
3. На основном сервере включить `sites-available/internal-db` в `sites-enabled`.
   Nginx разрешает доступ к порту 8124 из localhost и Docker-подсети OG
   `172.31.0.0/16`. Дополнительно разрешить этот входящий трафик в firewall хоста
   по инструкции ниже. Вход использует общий кеш и не наследует лимиты публичного
   db-vhost. Имя `internal-public` само по себе не снимает ограничения Nginx
   на публичном входе.
4. Опубликовать frontend и backend OG. Настроить `CLICKHOUSE_PASSWORD` в `.env`
   OG-сервиса. Его production Compose использует внутренний Nginx; dev — публичный endpoint.

Проверка после публикации: заполнить кеш под `public`, повторить тот же запрос
с тем же TTL под `internal-public` с неверным паролем — ожидается HIT/200.
Для ещё не закешированного запроса неверный пароль должен дать ошибку, верный —
успешный MISS; повтор под `public` должен дать HIT. Проверить каждый слой отдельно.
В debug-карточке `/debug/meta/vehicle?tag=ussr:R45_IS-7` должно появиться «ИС-7».

## UFW основного сервера

[ufw/setup.sh](ufw/setup.sh) сохраняет правила и политики основного сервера
`wotstat` по выводу `ufw status verbose` от 2026-10-15:

- UFW включён, logging `low`, новые профили `skip`.
- По умолчанию: входящие `deny`, исходящие `allow`, маршрутизируемые `deny`.
- `OpenSSH` — входящий TCP 22 от любых адресов.
- ClickHouse — входящие TCP 9000 и 8123 от любых адресов.
- `Nginx Full` — входящие TCP 80 и 443 от любых адресов.
- OG → Nginx — входящий TCP из `172.31.0.0/16` к `172.17.0.1:8124`.

Для применения нужны установленный UFW, профили `OpenSSH` и `Nginx Full`,
а также `IPV6=yes` в `/etc/default/ufw`. Тогда общие правила добавляются для
IPv4 и IPv6; правило OG относится только к IPv4.
Запуск из корня репозитория на основном сервере:

```sh
sudo sh ufw/setup.sh
```

Скрипт добавляет разрешающие правила до изменения политик и включения UFW.
Существующие дополнительные правила сохраняются, `ufw reset` не выполняется.
Синтаксис команд описан в [ufw(8)](https://manpages.debian.org/trixie/ufw/ufw.8.en.html).

## Доступ из OG-контейнера к Nginx

При активном UFW с `deny incoming` одного `allow` в Nginx недостаточно.
Разрешить входящие соединения из подсети OG к адресу хоста на порту 8124:

```sh
ufw allow in proto tcp from 172.31.0.0/16 to 172.17.0.1 port 8124 comment 'og-meta to nginx'
```

Здесь `172.17.0.1` — адрес `host.docker.internal` внутри production-контейнера.
Проверить его можно через `docker compose -p og-meta exec -T og-meta getent hosts host.docker.internal`;
если адрес отличается, использовать его в правиле. Это соединение к самому хосту,
поэтому требуется входящее правило (`allow in`), а не `ufw route`.
Правило действует сразу, перезапуск Nginx и контейнера не нужен.

После настройки проверить запрос к `CLICKHOUSE_PROXY_URL` из контейнера с
авторизацией `internal-public`: `SELECT 1` должен вернуть HTTP 200 и `1`.
Проверка через `curl http://127.0.0.1:8124/` на хосте не проверяет доступ из Docker.
